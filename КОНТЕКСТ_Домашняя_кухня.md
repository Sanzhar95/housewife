## 5. Ключевые правила предметной логики

**Единицы.** `КГ, Г, Л, МЛ, ШТ`. Семейства: вес (КГ/Г, ×1000), объём (Л/МЛ, ×1000), штуки. Остаток и минимум продукта хранятся в **единице продукта**. В «Составе» количество хранится в единице продукта, а «Ед. в рецепте» — как показывать (250 Г для продукта в КГ хранится как 0.25). В «Приходах» каждая строка хранит свою единицу; «Цена за ед.» — за единицу этой строки. Смена единицы продукта в том же семействе пересчитывает остаток/минимум (в форме) и состав (на сервере); смена семейства — без пересчёта, с предупреждением. Красивый вывод: 0,25 кг → 250 г, 1500 мл → 1,5 л (`fmtQ_` на сервере, `qtyNice` на клиенте). Округление хранения — 1e-6.

**Цены.** На клиенте `ps` = цена за 1 г / 1 мл / 1 шт; показ — за кг / л / шт. Себестоимость блюда = Σ ps × кол-во. Тренд = последняя vs предпоследняя покупка.

**План.** Строка плана = одно блюдо в слоте (день × приём). Основное блюдо может иметь гарнир; доп. блюда (салаты) — отдельные строки «доп», можно несколько. Потребность строки = состав блюда + состав гарнира; у **вчерашней** строки потребность пустая.
- `generateWeek({onlyAvail, meals, sides, leftovers})`: сохраняет приготовленное этой недели, остальное (включая вручную добавленные салаты) заменяет; новая неделя (сменился понедельник) — план с нуля. Подбор: блюда для своего приёма пищи (`meals`), редкие/непрошлонедельные вперёд, при `onlyAvail` — симуляция остатков на всю неделю; к блюдам «с гарниром» подбирается гарнир. Не хватило — слот пустой + notice.
- Готовка: `cookItem(id, opts)`, `cookMeal(day, meal, opts)` (opts: `{portions, times, target: {day,meal}|'none', src}`; старый вызов с `{day,meal}` понимается как target), `cookDish(dishId, sideId, opts)` (вне меню). Проверка нехватки → списание → отметка. `target={day, meal}` — «Останется на потом?»: блюдо+гарнир ставится туда как вчерашнее (если там неприготовленное основное — заменяется; если приготовленное — добавляется как доп).
- Отмена `undoItem` возвращает продукты (у вчерашнего — ничего).
- Смена гарнира `setSide` / `rerollSide`: у приготовленного (не вчерашнего) блюда возвращает старый гарнир и списывает новый (с проверкой нехватки).
- Вчерашнее: `setLeftover(id, on)`, `addLeftover(day, meal, dishId, sideId)`. Только Обед/Ужин в интерфейсе. Подсказки «Доесть: …» = приготовленное вчера и сегодня раньше (обеды/ужины).

**Порции.** `Рецепт на, порций` у блюда (пусто/0 = `DEF_PORTIONS` = 4). Количества в «Составе» записаны на эти порции. Готовим на P порций → каждое блюдо (основное и гарнир отдельно, от своей базы) масштабируется на `P / порций_рецепта`. P берётся так: `План.Порций` (выбрано при готовке) → иначе `Настройки.portions` → иначе 0 = по рецепту как есть (поведение старых версий). Масштаб применяют `needMap_(m, dish, side, P)` / `itemNeed_` на сервере и `needMap` / `itemNeed` на клиенте (список покупок, «хватает ли»). `Порций` сохраняется в строке плана при готовке, поэтому отмена и смена гарнира у приготовленного возвращают/списывают ровно то же количество. Проверка нехватки — на сервере; клиент показывает красную строку в окне.

**Хватает на N раз.** `Блюда.Хватает на, раз` (1–7, только у основных). Остатки = N−1 приёмов пищи «вчерашнего» (`left=true`, склад не трогают). Правила (`leftoverSlots_`, `placeLeftovers_`): со следующего дня, тот же приём (Обед/Ужин), завтрак → обед; подряд по дням; за воскресенье не переносится (в уведомлении об этом сказано). Явный старт — `opts.target={day,meal}`: тогда N−1 (минимум 1) приёмов подряд с него в тот же приём; `opts.target='none'` — не ставить. Вне меню (`cookDish`) нужен `opts.src={day,meal}` — иначе «само» не определить. Слот с неприготовленным основным блюдом заменяется остатками, с приготовленным — остатки добавляются как «доп». В `План.Остатки от` хранится id строки-источника: `undoItem` убирает ещё не съеденные остатки этой готовки. `generateWeek({leftovers})` (по умолчанию true) резервирует слоты следующих дней и ставит туда «вчерашнее» с `from`; у блюда с N>1 готовится одна из N порций, склад симулируется один раз.

**Уведомления.** Порог — `stock <= min`. После готовки письмо только по продуктам, пересёкшим минимум; ежедневный триггер `checkLowStock` шлёт всё, что ниже минимума (MailApp, если указан e-mail).

## 7. Миграции (данные не теряются)

Выполняются в `setup_()` (вызывается `getState()`/`doGet()` и пунктом меню «Настроить таблицу»), идемпотентно:
- Нет листа «План», есть «Неделя» (v1) → строки переносятся как **Ужин** того же дня (с отметкой «приготовлено»), лист переименовывается в «Неделя (архив)».
- Шапки листов дописываются до актуальных (новые столбцы: Блюда → Тип/Приёмы/С гарниром; Состав → Ед. в рецепте; План → Вчерашнее). Пустые значения трактуются как значения по умолчанию.
- Старые «Приходы» без столбца «Ед.» → вставляется столбец, заполняется текущей единицей продукта.
- Проверено на таблицах в формате v1 и предыдущей версии: исходные данные не меняются, повторный запуск ничего не дублирует.

## 13. Сайт и API (этап 1, п. 14 хронологии)

Структура репозитория: `public/` (сайт), `apps-script/` (`Code.gs`, `appsscript.json`, `api-patch.gs`), `build.js`, `.env.example`, `CLAUDE.md`, этот файл.

- **Клиент:** `public/index.html` (бывший `Index.html`) на Cloudflare Pages, автодеплой из GitHub. PWA: `manifest.json`, `sw.js` (сеть в приоритете, кэш оболочки на случай офлайна; POST к серверу не кэшируется), иконки в `public/icons/`.
- **Связь:** `public/api.js` подменяет `google.script.run` (включая `withSuccessHandler`, `withFailureHandler`, `withUserObject`) на `fetch` POST к `doPost` Apps Script. Тело `{token, fn, args}`, ответ `{ok}` или `{error}`. `Content-Type: text/plain` — чтобы браузер не делал preflight (Apps Script его не обрабатывает). `exportXlsx` выполняется в браузере (SheetJS), на сервер не ходит. Код приложения (`call`/`act`) не менялся.
- **Сервер:** `apps-script/api-patch.gs` дописывается в конец `Code.gs`: `doPost` + белый список функций `API_FUNCS_` (лениво, отсутствующая функция ломает только свой вызов). Токен — в Свойствах скрипта `API_TOKEN`, в коде его нет. `appsscript.json`: access `ANYONE_ANONYMOUS`, executeAs `USER_DEPLOYING`. Новая функция серверного API = новая строка в `API_FUNCS_`.
- **Конфиг сайта:** `public/config.js` создаёт `node build.js` из `.env` или переменных Cloudflare (`API_URL`, `API_TOKEN`; позже `SUPABASE_URL`, `SUPABASE_ANON_KEY`). В git не хранится (`.gitignore`). Cloudflare Pages: build command `node build.js`, output `public`.
- **Безопасность:** токен лежит не в git, но виден в браузере. Защита — не публиковать адрес и/или закрыть сайт через Cloudflare Access. При доступе «Все» страница `doGet()` тоже публична: после перехода на сайт закрыть её свойством `LEGACY_UI` (см. комментарий в `api-patch.gs`).
- **Проверено на имитации (Node):** `doPost` (токен, белый список, аргументы), подмена `google.script.run` (успех, ошибки, нет сети, не-JSON, exportXlsx), `build.js`. **Не проверено (проверить на месте):** реальное развёртывание Apps Script с доступом «Все», работа на iPhone в Safari и в режиме «На экран Домой», поведение клиента после локальной выгрузки Excel (в клиентском коде могла остаться логика «открыть ссылку»).
- **Этап 2 (план, не начат):** Supabase (Postgres + вход по e-mail-ссылке + RLS по `household_id`), сайт остаётся на Cloudflare Pages; меняется только `rpc()` в `api.js` и серверная логика переезжает в клиент (`logic.js`) или SQL-функции. Порядок: чтение состояния → продукты и блюда → состав и матрица → меню → готовка и гарниры → «вчерашнее», порции, «хватает на N раз» → генератор меню → Excel. Уведомления — Telegram-бот (Edge Function + pg_cron). Резервные копии — GitHub Actions по расписанию. 29 серверных тестов переписываются под новый слой.

## Загрузка блюд из Excel

Вкладка «Блюда»: «📥 Загрузить блюда из Excel» и «📄 Бланк блюд». Принимается только один формат (для людей: `docs/import-format.md`).

- **Формат:** один лист, заголовок точно: Блюдо, Тип, Приёмы пищи, С гарниром, Порций в рецепте, Хватает на, раз, Заметка, Продукт, Количество, Ед. Блюдо — группа строк (пустое «Блюдо» продолжает предыдущее; одинаковые названия объединяются, ё=е, регистр не важен); поля 2–7 берутся из первой строки блюда, продукт и количество — из каждой.
- **Правила:** блюдо, которое уже есть, пропускается (существующие блюда и состав не меняются); продукт ищется по названию, нет — создаётся (единица обязательна, остаток 0, минимум 0); единица должна быть из той же семьи (кг/г, л/мл, шт); ошибка в строке — блюдо целиком не загружается, остальные загружаются; один продукт дважды в блюде — суммируется; «хватает на» больше 7 ограничивается 7; лимит 500 блюд и 5000 строк; чужой бланк — «Это не наш бланк».
- **Экран:** шторка «📥 Блюда из Excel»: сводка «новых / уже есть / с ошибкой / новых продуктов», список с 🆕 ✔️ ⚠️; кнопка «Загрузить (N)» блокируется на время записи (защита от двойного тапа), при N = 0 — «Закрыть»; файл без блюд — «В файле нет блюд».
- **Файлы:** `public/import-dishes.js` (разбор, бланк; чистые функции), действие `importDishes` в `public/logic.js` (одна транзакция, запись в журнал «Загрузка блюд из Excel» — по ней считается метрика «блюд на семью»), экран в `public/index.html` (`pickDishesExcel`, `dishImportPreview`, `downloadDishTemplate`), `public/sw.js` (в оболочке, кэш `dk-shell-v3`). Схема базы не менялась.
